**Project:** kiss-server
**Milestone:** v1.5 Plugin Architecture Spike
**Decided:** 2026-04-15
**Status:** Accepted

## ARCH-01: Dynamic Library Loading — Rejected

**Decision:** Dynamic library plugin loading (`.so`/`.dylib` via `libloading`) is rejected for kiss-server.

### Technical Rationale

1. **No stable Rust ABI.** Rust has no stable ABI. Passing a `Box<dyn Handler>` across a `.so` boundary is undefined behavior regardless of compiler version. The plugin and host must be compiled with the exact same rustc version, with the same optimization flags, or behavior is undefined. This is not a theoretical concern — it is a documented property of the Rust language specification.

2. **Unsafe at every boundary.** Every function call across the `.so` boundary requires `unsafe`. Practical implementation demands `catch_unwind` boilerplate at every entry point, `#[repr(C)]` on every shared type, and a versioned C ABI contract that must be maintained manually. For a single-developer project with first-party plugins only, this is unbounded maintenance debt.

3. **`libloading` is a third-party crate.** D-03 blocks third-party (crates.io) crates from being added to kiss-server. `libloading` is published on crates.io. This constraint alone is sufficient to reject dynamic loading. The ABI instability is the primary disqualifier, but D-03 provides an independent, definitive blocker.

4. **Zero benefit for first-party plugins.** kiss-server plugins are first-party, compiled together. Dynamic loading adds complexity and `unsafe` with no compensating benefit. Hot-reload is deferred to a future phase and would require a different mechanism regardless.

### Research Outcome

Four independent researchers reached unanimous rejection. No dissent. Dynamic library loading was considered and definitively ruled out.

### Alternatives Considered

| Alternative | Why Rejected |
|-------------|-------------|
| `libloading` crate | Third-party (crates.io); D-03 blocks it; requires `unsafe` at every boundary |
| `abi_stable` crate | Third-party (crates.io); D-03 blocks it; still requires significant `unsafe` |
| `stabby` crate | Third-party (crates.io); D-03 blocks it; solves ABI but not D-03 |

All alternatives require third-party crates and `unsafe`. None are viable within project constraints.

## ARCH-02: Trait Object + Startup Registration — Selected

**Decision:** Compile-time trait objects with startup registration is the canonical plugin pattern for all future kiss-server plugins.

### Pattern Description

- Plugins implement `KissPlugin: Handler` (supertrait). `KissPlugin` adds `name() -> &str` and `path_prefix() -> &str` on top of the existing `Handler` contract.
- Plugin structs are instantiated in `main.rs` based on `[[plugin]]` TOML config blocks parsed from the server configuration file.
- Instantiated plugins are registered with the router via `Router::add_prefix()`, which uses `starts_with()` matching semantics for prefix-based route ownership.
- The router and server core remain ignorant of which plugins exist — that knowledge lives only in `main.rs`. This preserves the existing architecture's clean separation of concerns.
- Plugins are stored as `Box<dyn Handler>` in the router. The router does not need `KissPlugin` metadata at dispatch time.

### Why This Pattern

- **Uses existing primitives.** Leverages the existing `Handler: Send + Sync` trait and `Box<dyn Handler>` in the Router. No structural changes to the dispatch loop.
- **Zero new external crates.** D-03 is fully satisfied. The entire plugin infrastructure — `KissPlugin` trait, `Router::add_prefix()`, and `[[plugin]]` config parsing — is implemented in first-party code.
- **Safe concurrency.** Plugin state via `Arc<RwLock<T>>` satisfies `Send + Sync` without `unsafe`. No `Mutex` poisoning concerns for read-heavy workloads.
- **Config-driven activation.** Adding a `[[plugin]]` block to the TOML config activates a plugin. Removing it deactivates it. No recompile required for activation changes.
- **First-match dispatch semantics.** Plugins are tried in registration order. Registration order is the explicit priority mechanism, requiring no additional framework.

### Canonical Implementation Sketch

```rust
// Plugin trait (src/server/plugin.rs)
pub trait KissPlugin: Handler {
    fn name(&self) -> &str;
    fn path_prefix(&self) -> &str;
}

// Router addition (src/server/router.rs)
pub fn add_prefix(&mut self, prefix: &str, handler: Box<dyn Handler>) { ... }

// main.rs — reads [[plugin]] TOML blocks, wires plugins
for plugin_config in config.plugins {
    router.add_prefix(&plugin_config.prefix, build_plugin(&plugin_config));
}
```

### Future Evolution

After Phase 23 validates the `KissPlugin` API surface with real plugins, the `KissPlugin` trait will be extracted to a `kiss-plugin-sdk` first-party crate. Plugins will then live in separate repositories as `git =` or `path =` Cargo dependencies — bypassing D-03's crates.io restriction entirely, since first-party git/path dependencies are explicitly permitted.

## AUTH-01: Auth Placement — Middleware

**Decision:** Authentication enforcement runs as pre-dispatch middleware, not as a plugin handler and not as a hardcoded server-core gate.

### Rationale

**Plugin-route auth is a documented failure mode.** CVE-2025-61928 and the OpenClaw gateway plugin bypass are both cases where plugin-registered routes existed outside the auth-checked dispatch path, allowing unauthenticated access to protected resources. A plugin handler that owns `/auth/*` can serve login and signup endpoints, but it cannot protect routes it does not own.

Middleware runs before `router.dispatch()` on every request. New plugins automatically receive auth coverage without opt-in. An explicit exemption list for public routes (e.g., `/health`, `/s/*`) ensures public endpoints bypass middleware cleanly.

### Option Comparison

| Option | Can protect arbitrary routes? | Requires server-core changes? | Swappable? |
|--------|------------------------------|-------------------------------|-----------|
| Auth as plugin | No — only its own prefix | No | Yes |
| Auth as middleware | Yes — all routes by default | Yes (wire into handle_connection) | Yes |
| Auth as server-core gate | Yes | Yes (hardcoded in core) | No |

Auth-as-middleware is the only option that is both comprehensive (all routes) and swappable (no hardcoding in server core).

### CVE Evidence

- **CVE-2025-61928:** Auth bypass via plugin route registration outside the auth-checked dispatch path. Plugin registered its own routes; routes registered by other components were not covered.
- **OpenClaw gateway bypass:** Same architectural pattern, different project. Plugin-owned auth routes did not cover the full dispatch space.

Both CVEs share the same root cause: treating auth as a handler that owns routes rather than a gate that runs before all routes.

### Implementation Notes

The pre-dispatch hook is an ordered `Vec<Box<dyn Middleware>>` held inside `handle_connection()`. Auth middleware is registered first. The exemption list is an explicit `HashSet<String>` or prefix `Vec` of public paths that skip middleware. A test must verify that exempted paths (`/health`, static file routes) skip the hook and that plugin routes (`/s/*`) do not.

## AUTH-02: MVP Auth Strategy

**Decision:** MVP authentication uses a managed auth service (Clerk or Auth0) with JWT validation at the CDN edge. The Rust origin reads a trusted header, not JWTs directly.

### Architecture

```
Browser → CloudFront → Lambda@Edge (validates JWT) → EC2 (Rust origin)
                                                         ↓
                                                 reads X-Authenticated-User header
```

1. Managed auth service (Clerk recommended) handles user registration, login, session management, and JWT issuance. Clerk is interchangeable with Auth0 — the Rust side does not depend on the provider.
2. Lambda@Edge (or CloudFront Functions) validates the JWT on every request before it reaches the origin. Invalid JWTs are rejected at the CDN edge; the Rust origin never sees them.
3. If the JWT is valid, Lambda@Edge sets `X-Authenticated-User: <user_id>` on the forwarded request.
4. The Rust middleware reads `X-Authenticated-User` and populates `ctx.auth = Some(AuthClaims { user_id })`.
5. If the header is absent, `ctx.auth` remains `None`; the middleware returns `401 Unauthorized` for routes that require authentication.

### Why No Crypto in Rust for MVP

- `jsonwebtoken` crate pulls approximately 12 transitive crates including `ring` (C and assembly crypto). This is a significant dependency addition.
- D-03 blocks third-party crates until `serde`/`serde_json` are independently justified — likely during the chat engine phase when JSON parsing is required.
- Lambda@Edge is already in the CloudFront stack (Phase 15 CD pipeline). Adding JWT validation there requires zero new infrastructure.
- The `X-Authenticated-User` header approach is a documented AWS practice for origin-trust patterns behind CloudFront.

### Build-Order Implications

Middleware infrastructure (Phase 22) must exist before any authenticated plugin can be built. The `Context.auth: Option<AuthClaims>` field must be added during the plugin infrastructure spike (this phase), not later. Adding it after multiple plugins exist requires touching every plugin's test setup. The field costs nothing to add now and is expensive to retrofit.

```
Plugin infrastructure (Context.auth slot, middleware chain) — Phase 21
    ↓
Middleware infrastructure (JwtMiddleware stub, exemption list) — Phase 22
    ↓
URL Shortener plugin (validates infra with real data, no auth requirement)
    ↓
Chat engine plugin (auth required; triggers AUTH-03 if Rust JWT validation needed)
```

## AUTH-03: Post-MVP Auth Replacement Path

**Decision:** When a concrete requirement forces Rust-native JWT validation, the Lambda@Edge middleware is replaced with a Rust `JwtMiddleware` that validates tokens directly. The middleware chain architecture does not change.

### Trigger Condition

Add Rust JWT validation when `serde` and `serde_json` are already justified by another need — most likely the chat engine phase when JSON parsing is required for WebSocket message handling. At that point, `jsonwebtoken` adds marginal dependency cost on top of crates already in `Cargo.toml`.

Do not add `jsonwebtoken` before this trigger. The Lambda@Edge approach is correct and secure for MVP.

### Dependency Impact

| Crate | Purpose | Notes |
|-------|---------|-------|
| `serde` | Deserialization framework | Likely justified by chat engine JSON parsing |
| `serde_json` | JSON deserialization | Required alongside serde |
| `jsonwebtoken` | RS256 JWT validation | Depends on serde/serde_json |
| Transitive deps (~12 total) | ring (C/ASM crypto), base64, etc. | One-time cost |

`ring` adds C and assembly build steps, which increases build complexity. This is a one-time cost: once the crate boundary is crossed, additional crate additions within the `serde`/`jsonwebtoken` ecosystem become cheaper.

### Migration Steps

1. Add `jsonwebtoken`, `serde`, `serde_json` to `Cargo.toml`.
2. Implement `JwtMiddleware` that validates RS256 tokens issued by the managed auth service (Clerk or Auth0).
3. Remove the `X-Authenticated-User` header trust — the middleware now validates the JWT directly from the `Authorization: Bearer <token>` header.
4. Remove the Lambda@Edge JWT validation function.
5. Update the CloudFront behavior to pass requests without Lambda@Edge processing.

### What Does NOT Change

The `AuthClaims` struct, the `ctx.auth: Option<AuthClaims>` field, and the middleware chain architecture all remain identical. Plugin code that reads `ctx.auth` requires zero changes. Only the middleware implementation swaps — from header-trust to JWT-validation.

This is the critical property of AUTH-01: because auth is middleware, not a plugin handler and not a hardcoded server-core gate, it can be replaced without touching any other component.
