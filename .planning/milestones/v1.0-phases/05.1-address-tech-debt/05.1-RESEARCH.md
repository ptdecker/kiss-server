## Summary

Phase 5.1 is a pure cleanup phase with five discrete, non-overlapping tech debt items identified in the v1.0 milestone audit. No new features, no new abstractions. All items are fully characterized by reading the current source — no library research is required. The domain is Rust-specific: attribute removal, one `?`-propagation fix, and two documentation text edits.

The work divides naturally into two categories: code changes (three items touching three Rust source files) and documentation changes (two items touching two planning/doc files). Code changes must leave `cargo test` green (currently 87 passing). The pre-commit hook runs `cargo clippy -D warnings` and `cargo fmt`, so removing `#[allow(dead_code)]` from truly-used symbols is safe — Clippy will not complain about used functions. Removing the annotations from dead APIs (`Url::is_safe()`, `Url::query()`) is paired with removing the APIs themselves, so no warnings will be surfaced.

The one item with production safety implications is `stream.peer_addr()?` at `server/mod.rs:188`. The `?` operator propagates an `io::Error` out of `handle_connection`, which means a client that drops its connection between line 185 (request parse) and the debug log at line 188 would cause the server to skip sending any response. The fix is straightforward: replace `?` with `.unwrap_or_else(|_| "0.0.0.0:0".parse().unwrap())` or similar — the `peer_addr()` result is only used as a display argument inside the `debug!` macro and has no other semantics.

**Primary recommendation:** Group the five items into two plans — one plan for all code changes (three files), one plan for documentation-only changes (two files). This gives clean atomic commits and makes the code-change plan independently verifiable with `cargo test`.

### Pattern 1: Removing Stale `#[allow(dead_code)]`

**When to use:** When the annotated item is confirmed to be called/used somewhere in the codebase.

**Verification method:** After removal, `cargo clippy -- -D warnings` must pass. If clippy reports dead_code after removal, the item is still unused and needs deeper investigation.

**Confirmed items to fix (with exact line numbers at time of audit):**

- `handlers/mod.rs:30` — `#[allow(dead_code)]` above `fn mime_type(...)` — used at line 124 in same file
- `handlers/mod.rs:51` — `#[allow(dead_code)]` above `fn not_found(...)` — used at lines 96, 108, 113, 120 in same file
- `handlers/mod.rs:72` — `#[allow(dead_code)]` above `pub struct StaticFileHandler` — used in `main.rs` (registered as fallback)
- `handlers/mod.rs:83` — `#[allow(dead_code)]` above `pub fn new(...)` — used in `main.rs` (called in `main()`)

**Example — before:**

### Pattern 3: Fixing `?` Propagation in Debug Log

**What:** Replace `stream.peer_addr()?` with a non-failing form. The `peer_addr()` call returns `io::Result<SocketAddr>`. The result is only used as the first argument to `debug!()` for logging — it has no effect on the response.

**When to use:** When `?` would cause a function to return `Err` before a response is sent to the client.

**Exact location:** `src/server/mod.rs:188`

**Current code (problematic):**
```rust
debug!("Request ({:?}): {:?}", stream.peer_addr()?, http_request);
```

**Fixed code options (choose what compiles cleanly per Claude's Discretion):**

Option A — unwrap_or_else with parsed fallback:
```rust
let peer = stream.peer_addr()
    .unwrap_or_else(|_| "0.0.0.0:0".parse().unwrap());
debug!("Request ({:?}): {:?}", peer, http_request);
```

Option B — map to display string:
```rust
let peer = stream.peer_addr()
    .map(|a| a.to_string())
    .unwrap_or_else(|_| "unknown".to_string());
debug!("Request ({}): {:?}", peer, http_request);
```

Option A preserves `{:?}` formatting for `SocketAddr`. Option B uses a `String` with `{}` formatting — slightly simpler but changes format specifier. Either compiles cleanly. Option A is the closer structural equivalent to the original.

**Safety impact:** The current `?` causes `handle_connection` to return `Err(io::Error)` if the client dropped before `peer_addr()` could resolve. This causes the server to log a warning via `unwrap_or_else(|e| warn!(...))` at the call site in `run()`, and the client receives no response. Post-fix, a dropped client is handled gracefully — the debug log uses the fallback address and the function continues to the response-writing path.

### Anti-Patterns to Avoid

- **Do not remove `pct_encode` or `pct_decode` from url/mod.rs** — these are test helpers marked with their own `#[allow(dead_code)]` and are used in the url test module (`encode` and `decode` tests). They are not in scope.
- **Do not remove the inline dotdot check from `Router::dispatch`** — locked decision, no refactor.
- **Do not replace `?` with `.unwrap()` on `peer_addr()`** — `unwrap()` would panic if the socket is disconnected, which is worse than the current `Err` propagation. Use `unwrap_or_else` with a known-valid fallback.
- **Do not use `.parse::<SocketAddr>().unwrap()` on a variable** — the literal `"0.0.0.0:0"` is a valid SocketAddr that `parse()` cannot fail on; `unwrap()` is safe here specifically because the input is a string literal.
- **Do not accidentally remove the `// Forward-looking` comment on `set_fallback` in router.rs** — that annotation is still accurate (set_fallback WAS forward-looking when written; it is now used; but this cleanup only covers the items in the locked decisions list).

## Common Pitfalls

### Pitfall 1: Removing `#[allow(dead_code)]` from a truly-dead function
**What goes wrong:** After removing the annotation from `Url::is_safe()` or `Url::query()` WITHOUT also removing the function, clippy will emit a `dead_code` warning and the pre-commit hook will fail.
**Why it happens:** The locked decision is to remove both the annotation AND the function. Only removing the annotation is a half-step.
**How to avoid:** Always pair annotation removal with function removal for `is_safe()` and `query()`. For the four handler items, annotation removal only is correct (the functions stay).
**Warning signs:** `cargo clippy -- -D warnings` fails with `dead_code` after removal.

### Pitfall 2: Forgetting to remove `is_safe()` and `query()` tests
**What goes wrong:** The test module still calls `is_safe()` and `query()` on removed functions — compile error.
**Why it happens:** Tests are in a separate `#[cfg(test)]` block and easy to miss.
**How to avoid:** After removing a function, immediately search the test module for all tests using that function name.
**Test functions to remove from url/mod.rs:**
- `is_safe_dotdot`
- `is_safe_encoded_dotdot`
- `is_safe_normal_path`
- `is_safe_invalid_decode`
- `query_returns_string`

### Pitfall 3: Wrong format specifier in debug! after peer_addr fix
**What goes wrong:** If `peer_addr()` is mapped to a `String`, the format specifier must change from `{:?}` to `{}`. Using `{:?}` on a `String` works but adds extra quotes in the output — acceptable but inconsistent with the original intent.
**How to avoid:** If using Option A (SocketAddr via parse), keep `{:?}`. If using Option B (String), use `{}`.

### Pitfall 4: PATH-03 traceability row — wrong field to update
**What goes wrong:** Updating the Status field instead of the Phase field.
**Why it happens:** The audit description says "maps to Phase 4 as Pending" but the current file shows "Complete" in Status — the actual problem is the Phase column still says "Phase 4".
**How to avoid:** Change "Phase 4" to "Phase 5" in the PATH-03 row. Leave Status as "Complete".

### Pitfall 5: pre-commit hook formatting
**What goes wrong:** Pre-commit hook runs `cargo fmt` and reformats changed lines, blocking commit.
**Why it happens:** This project's pre-commit hook runs `cargo fmt --check` or applies `cargo fmt` automatically. Observed in Phase 5 plans 01, 02, and 03.
**How to avoid:** Run `cargo fmt` before staging. Especially relevant for the multi-line peer_addr fix.
