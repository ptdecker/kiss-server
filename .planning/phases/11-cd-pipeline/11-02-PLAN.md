  <action>
Two GitHub secrets must be set for the CD workflow to authenticate with EC2.

**Secret 1: EC2_SSH_KEY**
The private SSH key used to connect to EC2. Run locally:
```bash
gh secret set EC2_SSH_KEY < ~/.ssh/id_ed25519
```

**Secret 2: EC2_KNOWN_HOSTS**
The EC2 host fingerprint to avoid interactive SSH prompt. Run locally:
```bash
ssh-keyscan -t ed25519 54.83.192.65 2>/dev/null | gh secret set EC2_KNOWN_HOSTS
```

Per D-01, D-02, D-03: The same `~/.ssh/id_ed25519` key used locally for SSH to `ec2-user@54.83.192.65` is stored as `EC2_SSH_KEY`.
Per D-04 and research Pattern 2: Static known_hosts fingerprint (ssh-ed25519) stored as `EC2_KNOWN_HOSTS`.
  </action>
  <how-to-verify>
Run `gh secret list` and confirm both `EC2_SSH_KEY` and `EC2_KNOWN_HOSTS` appear in the output.
  </how-to-verify>

    <automated>gh secret list 2>&1 | grep -c "EC2_SSH_KEY\|EC2_KNOWN_HOSTS"</automated>
  </verify>
  <resume-signal>Type "secrets set" when both secrets are configured</resume-signal>
  <acceptance_criteria>

<task type="auto">
  <name>Task 2: Create prod branch, apply protection, and trigger first deploy</name>
  <files>origin/prod branch, GitHub Ruleset "Protect prod"</files>

  <action>
Execute these steps in sequence:

**Step 1: Create prod branch from main and push it**
```bash
git branch prod main
git push origin prod
```
This creates the `prod` branch pointing at the same commit as `main`. Per D-08, future deploys use PR from main to prod. Per Pitfall 4 from research, the branch must exist before the workflow can trigger.

**Step 2: Apply prod branch protection**
```bash
bash scripts/setup-prod-protection.sh
```
Per D-09: admin-only push access. The script creates a GitHub Ruleset targeting `refs/heads/prod` with deletion and non_fast_forward rules, bypass for RepositoryRole actor_id 5 (admin).

**Step 3: Verify the CD workflow triggered**
The push to `prod` in Step 1 should have triggered the CD workflow (since cd.yml was merged to main in Plan 01 and is now also on prod).

Check workflow status:
```bash
gh run list --workflow=cd.yml --limit=1
```

If the run shows, wait for it to complete:
```bash
gh run watch $(gh run list --workflow=cd.yml --limit=1 --json databaseId -q '.[0].databaseId')
```

If the workflow did NOT trigger (because cd.yml was not on the prod branch when prod was created from main before cd.yml was merged), then force a re-trigger:
```bash
git push origin main:prod
```

**Step 4: Verify deployment succeeded**
After the workflow run completes successfully:
```bash
# Verify service is running on EC2
ssh ec2-user@54.83.192.65 "sudo systemctl is-active kiss-server"

# Verify site still works
curl -fs http://54.83.192.65/ | head -5

# Verify GitHub Release was created
gh release list --limit=1
```

**Step 5: Verify the release has the binary attached**
```bash
gh release view $(gh release list --limit=1 --json tagName -q '.[0].tagName') --json assets -q '.assets[].name'
```
Should output `kiss-server` (the binary asset name from `target/release/kiss-server`).

Note: Per D-14, the release asset will be named `kiss-server` matching the source file `target/release/kiss-server`. This now aligns with the user's original decision — the Cargo package was renamed in phase 10.1.
  </action>
